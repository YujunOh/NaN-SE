## 1. 서론: 왜 프로세스인가

(6/2 설계 절과 함께 정리)

바이브코딩은 자연어 지시로 코드를 빠르게 얻는 방식이다. 빠른 대신 요구 정리와 설계, 테스트, 문서가 뒤로 밀린다. 코드가 돌아가는 것과 요구를 만족하는 것은 다른 문제인데, 이 차이를 검증하지 않은 산출물이 그대로 쌓인다. softgate는 코드를 만드는 과정 자체에 소프트웨어공학 절차를 끼워넣어 이 격차를 줄이려는 시도다. 자세한 배경과 통계는 저장소 README와 docs/VISION.md에 둔다.

## 2. 요구분석

### 2.1 요구분석을 먼저 한 이유

바이브코딩의 첫 번째 함정이 요구를 건너뛰고 곧장 구현으로 들어가는 것이라, 도구를 만드는 작업 자체도 같은 함정에 빠지지 않으려 했다. 그래서 코드보다 페르소나와 페인포인트를 먼저 정의하고, 거기서 유스케이스를 도출한 다음 구현 범위를 정했다. 요구를 먼저 고정하니 나중에 설계가 흔들렸을 때(2.5절 피벗) 무엇을 지켜야 하는지 판단 기준이 남아 있었다.

### 2.2 페르소나와 페인포인트

핵심 사용자는 AI 코딩 도구에 의존도가 높은 학생 개발자 본인(P1)이다. 다른 프로젝트에서 AI가 OAuth provider를 미리 다섯 개나 추상화해 둔 것을 지우고 단일 구현으로 되돌리느라 반나절을 쓴 경험이 출발점이었다. 추측성 추상화가 실제로 도움이 된 적이 거의 없었다는 자각에서 페인포인트가 나왔다. 주니어 개발자(P2)와 소프트웨어공학 학습자(P3)를 보조 페르소나로 두었다.

페인포인트는 5W1H로 정리했다. 누가(바이브코더, 주니어, 학습자), 무엇을(요구 없이 구현 진입, SRP와 응집도 위반 미인지, 위반을 알아도 고치는 법 막막), 언제(AI 도구 사용 시점, 코드 리뷰 직전), 어디서(에디터 세션), 왜(빠른 결과 욕구와 도구의 강제 부재), 어떻게 대응할지(Stage Gate, Metric Analyzer, Learning Card)를 한 표에 묶었다. 상세 표는 docs/REQUIREMENTS.md 2절에 있다.

### 2.3 유스케이스와 include·extend 관계

유스케이스 여섯 개 중 핵심 흐름은 UC-03(위반의 결정론적 검출), UC-04(학습 카드 생성), UC-05(카드 검수)다. 이 셋을 실제로 구현했고, Stage Gate(UC-01, UC-02)는 얇은 데모, Process Log(UC-06)는 보고서 설계로만 남겼다.

관계는 강의에서 다룬 include와 extend의 정의에 맞춰 정당화했다. include는 필수 포함 관계이므로, 학습 카드 생성(UC-04)은 검출(UC-03)이 만든 확정 결과를 항상 입력으로 받는다는 점에서 UC-04가 UC-03을 include한다. 검수(UC-05)도 생성된 카드를 항상 전제로 하므로 UC-04를 include한다. extend는 조건부 확장 관계이므로, 요구 없이 코드 변경을 시도하는 비정상 분기(UC-02)가 정상 흐름(UC-01)을 extend한다. 다이어그램은 Mermaid가 정식 유스케이스 문법을 지원하지 않아 flowchart로 PlantUML 표기를 흉내 내 그렸고, 원본은 REQUIREMENTS.md 3.2에 있다.

### 2.4 비기능 요구와 worst-case

기능 요구가 동사라면 비기능 요구는 형용사라는 강의 구분에 따라, 응답성(hook 500ms 이내), 신뢰성(결정론적이라 동일 입력에 동일 출력), 이식성, 유지보수성, 시험가능성을 별도로 정리했다. 신뢰성 요구가 뒤의 설계 피벗을 끌어낸 직접 원인이 된다.

worst-case는 다섯 개를 시퀀스 다이어그램으로 시각화했다. hook 우회, 설명층 오답, hook 시간 초과, DB 손상, 입력값 검증 누락이다. 각 경우의 보상 트랜잭션을 설계에 SAGA 패턴으로 연결했다.

### 2.5 요구가 설계를 흔들었을 때: 신뢰성 요구와 피벗

요구분석에서 박아둔 신뢰성 요구("결정론적이라 동일 입력에 동일 출력")가 개발 중반의 방향 전환을 끌어냈다. 처음 설계는 LLM이 SOLID 위반을 점수로 채점하는 구조였다. 그런데 같은 코드를 같은 프롬프트로 두 번 채점해도 점수가 흔들렸다. 이는 신뢰성 요구를 정면으로 위반한다.

이 의심을 주제를 버리라는 신호가 아니라 설계를 바꾸라는 신호로 읽었다. 검출은 결정론적 정적 메트릭(LCOM4와 순환복잡도)으로 옮기고, LLM은 확정된 위반을 학습 카드로 설명만 하게 분리했다. 확률적 채점을 신뢰하지 않는다는 판단의 근거로 선행 연구("Are We SOLID Yet?")를 참고했다. 이 분리가 softgate 전체의 핵심 설계가 됐다. 경위는 docs/DISCUSSION_LOG.md Day 5에 기록했다.

### 2.6 "검수는 사람" 원칙

검증과 확인은 결국 사람이 한다는 강의 메시지를 모든 모듈의 설계 기준으로 채택했다. 시스템과 문서가 맞는지(검증), 그것이 사용자 요구에 타당한지(확인) 둘 다 사람의 판단 영역이다. 그래서 도구는 단서를 만들지만 최종 판단은 사용자가 한다. 검출이 위반을 띄워도 고칠지는 사용자가 정하고, 학습 카드의 교정 예시도 사용자가 채택하거나 거절한다. 이 원칙이 "AI가 AI를 검증하는 것 아니냐"는 의심에 대한 답이 된다.
