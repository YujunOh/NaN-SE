## Day 1 — 2026-05-27

**사용**: 사전검수용 subagent 2회 호출

**관찰**:
- 1차 agent는 일반론·교과서 톤으로만 응답. 자료의 본문 인용 흔적이 부족했음
- "본문 발췌 인용 필수, 자료를 직접 읽어서 인용"이라고 명시 재지시하니 2차에서 자료 핵심 인용이 풍부해짐
- 같은 task를 두 번 시켰을 때 출력 깊이가 완전히 달랐음. 한 번에 안 끝나는 것이 일반 룰에 가까움

**메모**:
- AI 검수도 한 번 더 의심해서 재지시하는 흐름이 V&V 실천에 가까움
- 이 패턴 자체가 보고서 lessons learned 후보 (Issue #3)

**다음**: Day 2부터 코드 작성 0줄. AI 사용은 문서 작성·다이어그램 검토 보조에 한정. agent에게 prompt 줄 때 "본문 발췌 인용" 같은 검증 기준을 prompt에 명시.

## Day 2 — 2026-05-28

**사용**: 문서 작성 보조 + Mermaid 다이어그램 생성 + 어조 검수 후 전면 보완

**관찰**:
- Mermaid 다이어그램 생성 시 한 번 검수해서 채택. 자동 생성 그대로 commit하지 않음
- 어조 검수 받고 전면 보완 진행. AI 어투(명사 종결, em-dash, "솔직히:" 같은 어구, 출처 명시 등)가 문서 전반에 박혀있었음
- 검수 전까지 어조 문제를 자각하지 못했던 상태

**메모**:
- 어조 검수는 사람이 직접 해야 함. AI는 자기 출력의 AI 티를 감지하지 못함
- 다음부터 문서 작성 시 의식적으로 명사 종결 점 제거 + 짧은 하이픈 사용 + 출처 명시 회피

**다음**: Day 3 ARCHITECTURE·INTERFACES 작성(일부 선행) + Hook PoC

## Day 5 — 2026-05-31

**사용**: 검출 로직 구현 + 설계 피벗 + 문서 정렬

**관찰**:
- LLM에 SOLID 위반을 점수로 매기게 하니 같은 코드를 두 번 점수를 매겨도 점수가 흔들렸다. 요구분석에 박아둔 신뢰성 요구(동일 입력에 동일 출력)와 정면으로 어긋났다
- 의심이 들어 멈추고 구조를 바꿨다. 검출은 결정론적 메트릭(LCOM4와 순환복잡도)으로 옮기고 LLM은 설명만 하게 분리했다. AI가 만든 첫 설계를 그대로 두지 않은 게 이날의 핵심
- radon으로 복잡도를 뽑을 때 메서드와 함수, 클래스 집계 블록 구분(block.letter)을 AI가 처음엔 틀리게 잡아서 직접 확인하고 고쳤다

**메모**:
- AI에게 점수 매기기 같은 판단을 맡기면 비결정성이 그대로 품질 위험이 된다. 판단은 결정론적 코드로, 설명만 LLM으로. 이 분리가 보고서 핵심 논지가 된다
- 같은 날 옛 설계(SOLID Judge)가 남은 문서들이 새 구조와 모순됐다. 한 번에 다 못 잡고 grep으로 훑어 정정했다

**다음**: 강의 강조 주제 대비 점검(LECTURE_COVERAGE) + 강의 기반 예시 추가

## Day 6 — 2026-06-01

**사용**: 보고서 골격 작성 + 요구분석 절 정리

**관찰**:
- 구현이 끝난 상태라 흩어진 설계 문서를 보고서 한 편의 서사로 묶는 작업을 했다. AI에게 맡기니 문서 내용을 그대로 복사해 나열하려는 경향이 있어, "요구가 설계를 어떻게 흔들었는지" 같은 인과를 직접 넣어 다시 썼다
- 보고서는 사람이 읽는 산문이라 중간점과 화살표, 명사 종결 같은 AI 티가 특히 눈에 띈다. 작성 단계에서 의식적으로 뺐다

**메모**:
- 문서를 모으는 일과 논지를 세우는 일은 다르다. 전자는 AI가 빠르지만 후자는 직접 해야 한다
- 마감까지 하루 한 절씩 실제로 작성한다. 미리 다 만들어 날짜만 나누는 방식은 쓰지 않기로 했다

**다음**: Day 7 설계 절 + 아키텍처 다이어그램 캡처
