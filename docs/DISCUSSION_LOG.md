## 2026-05-29 (금) — Day 3, 핵심 아이디어 빈약 자각

오전 9시 시점. README를 다시 읽으면서 핵심 아이디어가 빈약하다는 자각이 왔다. SAGA 패턴이 정말 SDLC에 적용해서 효용 있는가? 모듈별 (Stage, EV Tracker, FP Counter, Process Log)이 정확히 무엇을 자동화해서 얼마나 도움 되는가? SOLID Judge는 좋아 보이지만 UseCase Logger는 결국 시각화 모듈인 거 아닌가?

### 광범위 리서치 위임

비슷한 도구가 이미 있는지 광범위 탐색을 agent에 위임했다. 키워드는 LLM 기반 SOLID 점수 매기기, traceability matrix 자동화, SDLC stage gate, Claude Code hook 통합 등 광범위.

결과가 결정적이었다.

첫째, **vibegate 이름 자체가 충돌**. PyPI에 `vibegate`라는 "deterministic production readiness gate" 패키지가 이미 알파 진행 중. 어휘와 포지셔닝이 그대로 겹친다. 이름 변경 필수.

둘째, **Traceability Matrix는 거의 동일 도구가 이미 있음**. Claude Plugin Hub의 `traceability-check` skill이 REQ-*/UC-* 스캔, commit message 매칭, gap/orphan 검출까지 한다. 단순 재구현은 표절 인상.

셋째, SDLC 플러그인은 다수 존재. 대부분 phase 강제. NaN-SE가 차별 가능한 영역은 "누락 검출 + 부드러운 제안"이고 Superpowers 같은 강제 게이트와 정반대 메시지 가능.

### 결정 — 이름·scope 재설정

이름은 softgate로 변경. soft 게이트 = "차단 X, 제안 O" 컨셉 텍스트에 내장. 짧고 기억 쉽고 충돌 확률 낮음.

scope는 6 모듈에서 3 핵심으로 축소 + 깊이 강화. SOLID Judge·Traceability·Stage에 집중. EV/FP/Process Log는 옵션으로 미룬다.

Traceability는 REQ ↔ UC ↔ code ↔ test 매핑을 commit message 태그로 자동 갱신하는 데모로 둔다.

### 추가 발상 — 위반을 학습 기회로

3 핵심 모듈로도 차별점이 약하다는 자각. 본인 의도는 "기술부채와 코드리뷰를 이해 못 하는 건 개발자가 바이브코딩된 코드를 직접 안 짠 데다 꼼꼼히 리뷰하지도 않아서"라는 근본 원인에서 출발. 그렇다면 SOLID Judge가 위반을 검출했을 때 그것을 학습 기회로 전환하면 어떨까. 짧은 학습 카드를 자동 생성해서 사용자가 검수·채택하고, 채택된 카드의 재요청 prompt가 AI에 다시 전달되는 폐쇄 루프.

여기에 Progress Dashboard로 학습이 누적되는 게 보이는 보상 구조를 더하면 강제·차단·점수 매기기 위주의 기존 도구와 명확히 차별된다.

scope 폭발 우려가 있어서 한 가지 원칙을 박았다. 학습 카드 자동 생성은 LLM이 자연어 콘텐츠만 채우고, 데이터 모델·파이프라인·검수 로직·DB 저장·CLI 렌더링은 전부 본인 구현. AI 생성물 취급 회피.

## 2026-05-31 (일) — Day 5, 주제 확신 흔들림과 재정의

오늘 가장 큰 토의. 아침에 주제 자체에 확신이 안 섰다. 피벗을 해야 하나 진지하게 고민했다.

의구심의 정체를 둘로 갈라봤다. 하나는 "NaN-SE가 세상에 가치 있는 제품인가"이고 다른 하나는 "12일 안에 실제로 굴러가는 걸 만들 수 있나"였다. 그리고 더 근본적인 설계 의심이 하나 더 있었다. 목표는 결정적(deterministic)인 검증인데, 확률적인 LLM 점수 매기기 레이어를 한 겹 더 얹는 게 무슨 의의가 있나. 어차피 최종 V&V는 사람이 하는데 AI가 한 번 더 본다고 100% 신뢰가 생기는 것도 아니고, SOLID 점수가 도움이 되려면 구조화된 기준에 정확히 맞아야 하는데 그 기준을 사람이 미리 하나하나 줄 수 있는지도 의문이었다.

### 검출과 설명의 분리

이 의심이 주제를 버리라는 신호가 아니라 설계를 바꾸라는 신호라는 결론에 도달했다. 지금 구조는 LLM이 점수 매기기(판정)과 설명(학습 카드)을 다 하고 있어서 문제였다. 이걸 쪼갰다.

검출은 결정적으로 간다. SOLID 전체를 LLM이 점수 매기는 게 아니라, 기계적으로 측정 가능한 proxy만 정적 분석으로 뽑는다. LCOM4(응집도), CBO(결합도), 순환복잡도, 메서드 수 같은 수십 년 된 교과서 지표들. 같은 입력에 같은 출력이 나오고 temperature 같은 게 없다.

설명만 LLM이 한다. "LCOM4가 3이다"는 결정적으로 나오고, "그게 왜 문제고 어떻게 고치는지"를 학습 카드로 풀어주는 게 LLM 몫. 여기서 LLM이 확률적인 건 문제가 안 된다. 판정이 아니라 튜터니까. 설명이 틀리면 사람이 카드를 거절하면 끝이고 잘못된 게이트로 막는 피해가 없다.

이 분리로 "AI가 AI를 검증하는 의의가 뭐냐"는 질문이 사라진다. 검증 숫자는 결정적 지표가 내고, LLM은 검증을 한 번도 안 한다. NaN-SE의 의의는 "검증을 대신 해준다"가 아니라 "사람이 귀찮아서 안 하던 검증의 비용을 낮춰서 실제로 하게 만든다"로 정리됐다.

### 기준 확보 조사와 한계 인정

결정적 기준이 충분한지 조사했다. CK 메트릭(WMC/CBO/RFC/LCOM), Martin 패키지 지표(불안정성·추상도), connascence 정적 형태, LCOM4·TCC·LCC 응집도 지표까지 표준이 차고 넘쳤다. 임계값도 자의적이지 않고 벤치마크 기반 도출법이 있었다.

SOLID별로 기계화 가능성을 정직하게 갈랐다. SRP·DIP·결합도·응집도는 결정적 proxy가 탄탄하고, OCP·ISP는 부분만, LSP는 본질적으로 기계화 불가라 LLM 힌트와 사람 판단에 맡긴다. 이 "어디까지 기계화되고 어디부터 사람 판단인가"의 경계선 자체가 보고서에 쓸 SW공학 통찰이 됐다.

### 이미 있는 도구 조사와 통합 결정

각 조각이 이미 시판품이 있는지 확인했다. 메트릭 계산은 cohesion, lcom, radon, lizard, PyExamine 등으로 완전히 존재했고, AI가 커밋 리뷰하며 설명하는 것도 여럿 있었다. 신제품은 아니라는 뜻.

하지만 이건 감점 사유가 아니라는 판단. 과제는 SW 자유 선정이고 점수 매기기는 프로세스다. 그래서 올바른 SW공학적 판단은 "있는 걸 다시 짜지 말고 가져다 쓰는 것"이라고 결정했다. radon 같은 건 의존성으로 넣고, 원본 작업은 그 위의 조합(메트릭 트리거에서 학습 카드, AI 재요청 prompt 폐쇄 루프)에 집중. McCabe 복잡도를 직접 재발명할 이유는 없다.

다만 LCOM4 하나는 직접 구현하기로 했다. SRP의 핵심 proxy이고, 본인 구현 영역을 코드로 보여주기 좋고, 난이도도 학부 알고리즘 수준이라 하루면 된다.

### 첫 동작 코드

`nanse/metrics/lcom.py`를 직접 짰다. Python `ast`로 클래스를 파싱해서 메서드별 self 필드 접근과 메서드 호출을 수집하고, 같은 필드를 공유하거나 서로 호출하는 메서드를 union-find로 묶어 연결 요소 개수를 LCOM4로 낸다.

처음엔 god class가 LCOM4=1로 잘못 나왔다. `__init__`이 모든 필드를 초기화해서 무관한 메서드들이 한 덩어리로 묶인 것. 대부분의 LCOM 도구가 생성자를 제외하는 이유를 직접 겪었다. dunder를 제외하니 AuthService가 LCOM4=3으로 갈렸고, 컴포넌트가 login/logout, send_email, issue_token으로 나뉘었다. LEARNING_CARDS.md에 적어둔 AuthService 분리 예시와 정확히 일치했다.

pytest 8개 케이스(정상·god class·메서드 호출 연결·staticmethod 제외·빈 클래스·잘못된 입력 예외·클래스 없음·타입 확인) 전부 통과. 도구가 실제로 측정한다는 게 처음으로 코드로 증명됐다.

다음은 이 메트릭 결과를 받아 학습 카드를 생성하는 파이프라인.

### 폐루프 완성과 LLM 분리

메트릭 결과를 학습 카드로 잇는 파이프라인을 다 짰다. finding 매핑(`findings.py`), 학습 카드 모델, 점수 매기기 금지 prompt, 파서, 생성기까지. 생성기는 LLM 호출을 `complete`라는 주입 가능한 함수로 뺐다. 덕분에 테스트에서 네트워크 없이 가짜 응답을 넣을 수 있고, NaN-SE가 검출하려는 DIP를 스스로 지키는 셈이 됐다.

검출 트리거는 LCOM4뿐 아니라 radon 순환복잡도도 붙였다. 직접 재발명하지 않기로 한 결정을 코드로 실천한 부분. 다만 radon 결과에서 메서드는 letter가 'M'이라 'F'만 필터링하면 빈 결과가 나오는 함정이 있었다.

SQLite Store, Typer+rich CLI(analyze/learn/cards/review/seed-demo)까지 묶어 검출에서 검수까지의 폐루프를 end-to-end로 돌렸다. 가짜 LLM으로 테스트 25개 통과. Windows 콘솔(cp949)에서 em-dash가 깨지는 버그도 잡았다. `learn` 커맨드는 실제 Anthropic 호출까지 배선이 닿았지만 이 환경에 API 키가 없어 실호출은 사용자 몫으로 남겼다.

### 문서를 피벗에 맞춰 정렬

검출/설명 분리 결정이 문서 곳곳의 옛 "SOLID Judge(LLM 점수 매기기)" 서술과 충돌했다. REQUIREMENTS의 유스케이스·worst-case, COMPETITIVE 비교표, FUTURE_WORK 이벤트명, WBS 트랙, README 모듈표를 모두 새 구조로 맞췄다. 특히 SonarQube·radon과 검출이 겹친다는 점을 솔직히 인정하고, 차별점을 학습 카드 폐루프로 다시 잡았다. GitHub 이슈도 #6을 Metric Analyzer+Learning Card로 재작성하고, 구현 범위 밖이 된 트랙엔 피벗 날짜 코멘트로 강등 사유를 남겼다. 의사결정 트레일 자체가 과제 증거라 닫지 않고 기록을 남기는 쪽을 택했다.

## 2026-06-06 (금) — Day 11, 우리 문서에 V&V를 걸다

기말 다른 과목과 겹쳐 며칠 손을 뗐다가 마감 전 점검에 들어갔다. 코드를 더 짜기보다, 만들어 둔 산출물이 사실과 맞는지부터 의심했다. 강의에서 반복된 "검증은 결국 사람이 하고, 자기 결과를 의심하라"는 말을 우리 문서에 그대로 적용한 셈이다.

먼저 repo 이름을 `nanse`에서 `NaN-SE`로 바꿨다. REPORT의 저장소 링크가 이미 NaN-SE를 가리키고 있어서 실제 repo와 어긋나 있었는데, rename으로 맞췄다. GitHub이 옛 URL을 리다이렉트하므로 기존 링크는 살아 있다. 코드·CLI·패키지 식별자는 소문자 `nanse` 그대로다.

본격적인 점검에서 문제가 꽤 나왔다. 문서 여러 곳이 **만들지 않은 기능을 만든 것처럼** 적고 있었다. ARCHITECTURE 한 줄 요약은 "Claude Code Hook 통합"을 구현 목록에 넣어 뒀는데 hook 코드는 한 줄도 없었다. CLI 명령 절은 `nanse init`·`session`·`trace`·`dashboard` 같은 존재하지 않는 명령을 실재하는 것처럼 나열했고, 정작 실제 명령(`learn`·`seed-demo`·`serve`)은 빠져 있었다. SQLite 스키마는 피벗 때 버린 11테이블(점수를 매기는 `solid_judgments` 포함)을 현재 스키마처럼 싣고 있었다. LEARNING_CARDS는 실재하지 않는 파일 경로(`prompt_optimizer.py`·`events.py`)를 본인 구현이라 적었다. 검출은 SRP·OCP 둘뿐인데 문서 곳곳에서 "4 핵심 모듈"·"6 모듈"을 구현한 듯 말했다.

원인은 분명했다. Day 5 피벗으로 범위를 검출·설명 폐루프로 좁혔는데, 피벗 전 설계 문서가 현재형 서술을 그대로 달고 있었다. 코드는 정직했지만 문서가 코드를 앞질러 있었다. 강의에서 말한 "코드가 돌아가는 것"과 "요구를 만족하는 것"의 간극이 문서 층위에서 벌어진 형태다.

수정 원칙은 하나로 잡았다. **구현한 것(검출 2지표 + 설명 카드 + 검수 CLI + 읽기 API + 웹 대시보드)과 설계로만 남긴 것(Stage·Traceability·EV/FP/Process Log·hook 통합)을 모든 문서에서 명확히 가른다.** TCP 비유나 SAGA 같은 설계 서사는 지우지 않고 "설계 구상"임을 배너로 달았다. 폐기한 스키마는 "원설계 기록"으로 강등했다. 의사결정 트레일 자체가 과제 증거라, 틀린 기록을 지우기보다 정정 사유를 남기는 쪽을 택했다.

문서를 정직하게 만들고 나니 첫인상 문제가 보였다. 문서가 많아 처음 보는 사람이 압도되고, 이름이 왜 NaN-SE인지가 어디에도 안 보였다. README 맨 위에 이름의 뜻(부동소수점 NaN = 잘못된 채 번지는 값 / Not a Naive Software Engineer)을 넣고, "왜 SRP·OCP만 검출하나"를 정면으로 답했다. 결정론적으로 측정 가능한 위반만 잡고 LSP·DIP처럼 확률적 점수가 필요한 건 의도적으로 뺐다는, 적게 잡아도 흔들리지 않는 선택이다. 목적별 문서 진입 경로 표도 더했다.

대시보드도 손봤다. seed-demo로 채운 5 finding·5 카드·67% 채택률을 헤드라인에 띄웠는데, 예시 데이터의 임의 숫자라 의미가 없었다. 검출된 원칙(SRP·OCP)·가장 잦은 위반·평균 심각도처럼 검출 결과를 설명하는 지표로 바꾸고, 예시 데이터임을 화면에 명시했다. 마지막으로 문서 산문의 번역투와 명사 종결 버릇을 훑어 다듬었다.

오늘의 교훈: 산출물은 코드만이 아니다. 문서도 검증 대상이고, 자기 문서를 의심하지 않으면 코드보다 먼저 거짓말을 한다.

## 2026-06-07 (토) — Day 12, 교차검증과 두 번째 절차

마감 전, 내가 만든 걸 내가 평가하면 편향된다고 보고 윤영 교수 점수 매기기 관점을 흉내 낸 깐깐한 자가 평가를 돌렸다. 총점 78점이 나왔고, 가장 크게 깎인 곳이 둘이었다. (1) "프로세스를 밟았다"고 쓰는데 커밋 이력이 마감에 몰려 보여 주장과 증빙이 어긋난다. (2) 검출이 SRP·OCP 두 지표뿐이라 "과정에 절차를 끼워넣는다"는 간판 대비 구현 표면이 좁다. 둘 다 정당한 지적이라 받아들였다.

이 자가 평가에서, 우리 보고서가 요구↔설계↔코드↔테스트 추적성 표나 아키텍처 후보 비교, 실패 사례 anchor 같은 표준 요소를 빠뜨렸다는 것도 스스로 짚었다. 그래서 다음을 보완하기로 했다.

판단과 조치:
- **두 번째 절차로 요구 추적(Traceability)을 최소 구현했다.** 처음엔 commit 태그 자동 갱신까지 만들려 했지만, 같은 일을 하는 도구(traceability-check 등)가 이미 있어 전체 재구현은 표절 인상이 컸다. 그래서 남이 대신 못 하는 최소 단위, "우리 요구가 코드와 테스트로 빠짐없이 추적되는가"의 존재 검증만 `nanse trace`로 직접 만들고 나머지는 설계로 남겼다. 테스트 6개를 더해 31개가 됐다.
- **보고서에 아키텍처 후보 비교표와 실패모드 anchor를 넣었다.** god class·거대 분기 라우터라는 실제 바이브코딩 실패를 LCOM4·순환복잡도가 정조준한다는 연결로 "왜 이 지표인가"를 외부 근거에 묶었다.
- **README 표제에서 TCP 비유를 내렸다.** 비유가 간판이 되어 실체를 앞선다는 지적을 받아, TCP는 VISION 본문으로만 두고 표제는 실제 기능 한 줄로 바꿨다.
- **커밋 분산 증빙을 다시 캡처했다.** 핵심 빌드는 5/28~6/2에 36커밋으로 있었고 6/6~6/7은 점검·정리였음을, 날짜 헤더가 또렷한 커밋 페이지로 남겼다. 공백과 막판 집중은 감추지 않고 그대로 적었다.
- **표준 SE 산출물을 보강했다.** 핵심 dataclass 기반 클래스 다이어그램(ARCHITECTURE 3.3), 검출→카드→저장→검수를 잇는 통합 테스트 1개(가짜 LLM 주입), Dockerfile·docker-compose로 재현 가능한 컨테이너 빌드·실행, GitHub 이슈/PR 템플릿(결정 기록 포함)을 더했다. 컨테이너는 실제로 빌드해 `nanse analyze`가 도는 것까지 확인했다. CI/CD의 잠긴 부분(자동 파이프라인·운영 계측)은 여전히 비웠고, 그 경계는 REPORT 6.4에 정직하게 적었다.

오늘의 교훈: 자기 평가는 못 미덥다. 교수 점수 매기기 관점이라는 외부 잣대를 빌려 내 결과를 의심해 보면 약점이 빨리 보인다. 그게 강의가 말한 "독립적 검증"의 작은 실천이다.
